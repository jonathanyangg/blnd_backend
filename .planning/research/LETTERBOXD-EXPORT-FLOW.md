# Letterboxd Export Flow: iOS File Acquisition

**Project:** BLND iOS — Letterboxd Import Feature (v1.1)
**Researched:** 2026-03-09
**Overall confidence:** HIGH (confirmed via official documentation and Apple developer docs)

---

## Executive Summary

There is no programmatic, OAuth-gated, or API-based path to obtaining a Letterboxd export ZIP. Letterboxd's API (still in private beta, access by email request only) does not expose a data export endpoint. The only legitimate source of the ZIP is the user manually downloading it from `letterboxd.com/[username]/settings/data/` in a browser.

On iOS, once that ZIP lands in Safari Downloads (which routes to the Files app / iCloud Drive by default), the user has two viable paths to get it into your app: (1) use the native `.fileImporter` SwiftUI modifier to let the user pick the file from Files, or (2) register BLND as a ZIP handler so the user can tap "Open in BLND" from Files or the Safari download sheet. Path 1 is simpler to implement, path 2 is marginally smoother UX.

The recommended flow is: user downloads ZIP on Safari → ZIP appears in Files app → user taps "Import Letterboxd" in BLND → native document picker (`.fileImporter`) opens → user finds and selects the ZIP → app reads it, constructs multipart upload, POSTs to `POST /import/letterboxd`, shows progress and results.

---

## Q1: Does Letterboxd Have an OAuth Flow or API for Export?

**Answer: No.** (HIGH confidence)

- The Letterboxd API is invite-only beta. Access requires emailing `api@letterboxd.com` with a description of intended use. Responses can take months with no guarantee of approval.
- The official API (`api-docs.letterboxd.com`) uses OAuth2 Authorization Code and Client Credentials flows. The documented API covers member data reads (films logged, ratings, lists) but does NOT include an endpoint that returns or triggers the export ZIP.
- The export ZIP is generated by a web-only action at `letterboxd.com/user/exportdata/` — this is a form POST that triggers server-side ZIP generation and then delivers a download. There is no API equivalent.
- The Letterboxd iOS app supports x-callback-url and Siri Shortcuts for a small set of actions (adding a film, searching) but data export is not among them.

**Implications for BLND:**
- Do not design a flow that assumes any programmatic handoff from Letterboxd.
- Do not attempt to scrape or automate the export page — fragile, violates ToS, and unnecessary.
- The user's manual download is the entry point. Design around that constraint.

## Q2: Realistic User Flows for Getting the ZIP into iOS

Three flows exist, ordered from best to worst for overall UX.

### Flow A: Files App Picker (Recommended)

1. User opens BLND, navigates to Import screen.
2. BLND shows a two-step card:
   - Step 1: "Download your Letterboxd data" — a link button that opens `letterboxd.com/user/exportdata/` in Safari.
   - Step 2: "Select your export file" — a button that triggers the `.fileImporter` document picker.
3. In Safari, user logs in (if needed) and taps Export. Safari downloads the ZIP to `Files > Downloads`.
4. User returns to BLND (app stays open; switch via app switcher or the BLND link from step 2 re-focuses the app).
5. User taps "Select export file," the document picker opens, they navigate to Downloads and select the ZIP.
6. BLND reads the file (security-scoped resource access), uploads via multipart to `POST /import/letterboxd`, shows progress and results.

**Mechanism:** SwiftUI `.fileImporter(isPresented:allowedContentTypes:onCompletion:)` with `allowedContentTypes: [.zip]`. Available iOS 14+, works across iCloud Drive, On My iPhone, third-party providers. UTType.zip identifier is `public.zip-archive`. No third-party libraries required.

**Security-scoped resource handling (required):**
```swift
// In the fileImporter result handler
url.startAccessingSecurityScopedResource()
defer { url.stopAccessingSecurityScopedResource() }
let data = try Data(contentsOf: url)
```

---

### Flow B: "Open in BLND" from Files App

1. User downloads ZIP in Safari; it lands in Files.
2. User opens Files, long-presses the ZIP, taps Share, selects "Open in BLND."
3. BLND receives the file URL via `onOpenURL` (SwiftUI) or `application(_:open:options:)` (AppDelegate), navigates to the Import screen, and begins upload.

**Mechanism:** Register BLND as a ZIP document handler in `Info.plist` by adding a `CFBundleDocumentTypes` entry with `LSItemContentTypes: ["public.zip-archive"]` and `CFBundleTypeRole: "Viewer"`. SwiftUI handles the incoming URL via `.onOpenURL { url in ... }` on the root `WindowGroup`. iOS will show BLND in the "Open in..." sheet for ZIP files from Files and other apps.

**Tradeoffs vs Flow A:**
- Slightly less friction at hand-off (one fewer step in-app).
- Requires correct Info.plist registration to appear in the share sheet.
- Requires handling the URL from two different entry points (in-app picker vs. system push).
- Without Flow A as fallback, users who don't discover "Open in BLND" are stuck.

**Verdict:** Register the document type anyway (it's five Info.plist lines), but Flow A remains the primary instructed path because BLND controls the instructional copy.

---

### Flow C: AirDrop from Mac

If the user downloads the ZIP on their Mac first:
1. User downloads ZIP at `letterboxd.com/[username]/settings/data/` on Mac.
2. User AirDrops the ZIP to their iPhone.
3. iPhone shows "Open with..." sheet; if BLND is registered as a ZIP handler (Flow B setup), BLND appears.

**Verdict:** Valid but uncommon path. Falls out for free if Flow B registration is done. No additional implementation needed.

---

### Flow D: In-App WebView / SFSafariViewController (NOT viable)

Attempting to open the Letterboxd export page in an in-app browser and intercept the download does not work:
- `SFSafariViewController` does not expose downloaded files to the host app — the download stays in Safari's sandbox, not the app's sandbox.
- `WKWebView` can intercept the download response (iOS 14.5+ via `WKDownloadDelegate`) and save to the app's temp directory, but this requires Letterboxd authentication cookies to be valid inside the WKWebView session, which they will not be (separate cookie jar from Safari). The user would have to log in again inside the webview.
- This approach adds complexity, requires session management, and is fragile to Letterboxd UI changes.

**Verdict:** Do not build this.

## Q3: Deep-Link or Redirect-Based Approaches (Safari → App)

There is no deep-link path that automatically transfers a file. What IS possible:

- **Custom URL scheme:** Register `blnd://` (or similar). An HTML page or script can call `blnd://import` to open the app, but it cannot pass the file — only a URL reference. Since the export ZIP is served from Letterboxd's server with auth cookies, a URL reference alone cannot be re-fetched by the app.
- **Universal Links:** Same constraint — they open the app and pass a URL, not a file payload.
- **No viable redirect-with-file path exists on iOS.** The OS does not provide a mechanism to hand off a file download from Safari to another app in the download completion flow.

**Verdict:** Deep links are useful only for re-focusing the app after the user completes their Safari download (i.e., a "Return to BLND" link on the Letterboxd export confirmation page — but BLND cannot inject content into Letterboxd's pages). Not worth implementing beyond documenting as a non-path.

## Q4: What Comparable Apps Do

**Simkl (web):** Users download ZIP from Letterboxd, then upload it via a web file upload form at `simkl.com/apps/import/letterboxd/`. The iOS Simkl app does not surface a Letterboxd import flow — it is web-only. This confirms the manual download + file pick pattern is the industry norm.

**Trakt:** Trakt uses OAuth to directly connect to Letterboxd for list imports (because Letterboxd's API does expose public list endpoints). However, Trakt does NOT use the export ZIP path — it reads public list data, not private watch history. Not comparable to what BLND needs (full private history).

**Pattern across comparable apps:** Every app that imports from Letterboxd's private data (watched, ratings, reviews) requires the manual ZIP export flow. Zero apps have automated this because Letterboxd provides no API for it.

## Q5: Smoothest UX Given iOS Constraints

### Recommended UX Design

**Screen name:** "Import from Letterboxd"

**Layout (dark monochrome, Cal.com/X aesthetic):**

```
[Header]
Import from Letterboxd

[Body copy]
Bring your watch history, ratings, and reviews into BLND.

[Step 1 — numbered card]
1. Download your data
   Go to letterboxd.com/settings/data and tap Export Your Data.
   The file saves to your Downloads folder in Files.
   [Button: "Open Letterboxd Export Page"] → opens Safari to letterboxd.com/user/exportdata/

[Step 2 — numbered card]
2. Select your export file
   [Button: "Choose ZIP File"] → triggers .fileImporter

[Status area — shown after file selected]
  filename.zip (1.2 MB)
  [Button: "Import"] or auto-trigger upload

[Progress — shown during upload]
  ProgressView (indeterminate or bytes-based)
  "Importing your films..."

[Results — shown on completion]
  X films imported
  X skipped (already in library)
  X failed
  [Button: "Done"]
```

### UX Copy Suggestions

- "Download your data" (not "Export your Letterboxd ZIP" — user-facing language)
- "Your data is already on your device. Select it below." (shown if user came back to app and previously saw step 1)
- Error state: "That doesn't look like a Letterboxd export. Make sure you selected the ZIP from letterboxd.com/settings/data."
- Success: "X films added to your library." (singular: "1 film added")

### What NOT to Build

| Approach | Why Not |
|----------|---------|
| In-app webview to Letterboxd | Auth doesn't transfer; file download stays in webview sandbox; fragile to UI changes |
| OAuth integration with Letterboxd API | API is invite-only beta with no export endpoint; not achievable without Letterboxd partnership |
| Scraping letterboxd.com programmatically | ToS violation; fragile; unnecessary given manual export works well |
| Automated re-import / polling for new exports | Letterboxd has no notification mechanism; manual download is a one-time user action |
| Custom URL scheme to receive file from Safari | iOS does not support file payload in URL scheme calls |
| AirDrop-specific UI | Falls out for free from the document type registration; no separate UI needed |

## iOS API Reference

| API | Purpose | iOS Availability |
|-----|---------|-----------------|
| `SwiftUI .fileImporter(isPresented:allowedContentTypes:onCompletion:)` | Opens system document picker for ZIP selection | iOS 14+ |
| `UTType.zip` (identifier: `public.zip-archive`) | Type token for ZIP files in fileImporter | iOS 14+ (UniformTypeIdentifiers framework) |
| `url.startAccessingSecurityScopedResource()` | Required before reading file URL from picker | iOS 8+ |
| `CFBundleDocumentTypes` in Info.plist | Registers app as ZIP handler for "Open with" | iOS 3+ |
| `onOpenURL` SwiftUI modifier | Receives file URL when app is opened via "Open with" | iOS 14+ |
| `URLSession.uploadTask(with:fromFile:)` | Streams file from disk for multipart upload without loading into memory | iOS 7+ |
| `URLSessionTaskDelegate.urlSession(_:task:didSendBodyData:)` | Reports upload byte progress | iOS 7+ |

## Implementation Notes for v1.1

### File Size Considerations

Letterboxd export ZIPs for heavy users can reach 1-5 MB. The backend already imposes a 10 MB upload limit. Reading the entire ZIP into memory with `Data(contentsOf: url)` is fine for this size range. For future-proofing, use `uploadTask(with:fromFile:)` which streams from disk rather than buffering in memory.

### Multipart Upload (matches existing backend contract)

The existing `POST /import/letterboxd` endpoint accepts multipart/form-data. The iOS implementation should:
1. Copy the security-scoped file to a temp directory (required — the security scope may not be active for the full async upload duration).
2. Build multipart body with boundary, field name `file`, filename, and content-type `application/zip`.
3. Set `Authorization: Bearer <jwt>` header from the existing `APIClient` pattern.
4. Use `URLSession.uploadTask` for the actual POST.

### Progress

The backend processes synchronously (parse CSVs, resolve TMDB, insert to DB) and returns results in the HTTP response body. There is no streaming progress from server — only upload progress (bytes sent) is available client-side. Use an indeterminate `ProgressView` during server processing, switching to a byte-based progress bar only during the upload phase.
